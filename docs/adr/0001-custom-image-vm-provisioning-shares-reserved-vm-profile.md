> **Статус: superseded.** VM Provisioning (`POST /api/v1/deployments`) для Custom OS Image убран: теперь VM с кастомным образом резервируется из готового пула через `GET /api/v1/vms?image=<value>`, тем же способом (VM Reservation), что и Preset OS — см. `resolveImage` и `_startWithReservedVm` в `sessions.service.ts`. Соглашение об именах `reserved_vm_<image>_<uuid>`, описанное ниже, больше не создаётся кодом — оно сохраняется здесь только как исторический контекст.

# VM Provisioning для Custom OS Image переиспользует profile `reserved_vm`

Предыдущее ТЗ на интеграцию с VM Fleet (`.claude/vm-fleet-integration-spec.md`) намеренно исключало создание VM через `POST /api/v1/deployments`: backend только резервировал уже готовые машины из пула (VM Reservation). Для Custom OS Image готового пула не существует, поэтому появляется второй способ получения VM — VM Provisioning: создание новой машины по требованию с ожиданием готовности перед подключением.

Решено не заводить в VM Fleet отдельный `profile` под такие машины, а использовать тот же `reserved_vm`, что и у пула Preset OS, с тем же соглашением об именах — `reserved_vm_<image>_<uuid>` вместо `reserved_vm_<os>_<uuid>`. Альтернативой было завести отдельный profile под кастомные образы (явнее разделяет VM Provisioning от VM Reservation в инвентаре VM Fleet, но требует конфигурации на стороне VM Fleet и отдельной константы). Выбранный вариант позволяет без изменений переиспользовать существующее удаление VM (`vmFleetClient.deleteVm` ищет машину по имени, не зная способа её создания) и не требует правок инфраструктуры VM Fleet.
